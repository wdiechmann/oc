# Prioritized Functions and Systems

This proposed sequence implements [organization.md](organization.md), covering the responsibilities in [named_spaces.md](named_spaces.md) and all 21 currently identified systems in [suggested_systems.md](suggested_systems.md), while supporting a registry of 25+ native, independently built and third-party applications. The sequence also incorporates [gdpr.md](gdpr.md), [system_1_plan.md](system_1_plan.md), and the near-real-time MV design in [suggested-data-store.md](suggested-data-store.md). Priorities reflect enabling dependencies, long lead times, safety, and readiness deadlines. They are relative priorities rather than dated commitments: **P0 — establish foundations**, **P1 — enable planning and recruitment**, **P2 — prepare delivery**, and **P3 — complete live-operation readiness**. Work within a priority can proceed in parallel once its dependencies are satisfied; a later priority does not make a service optional.

Tenant/signup foundations can precede camp appointments. Before appointing camp function staff, confirm Board representation, appoint both camp chiefs, and obtain Board approval of the management team. Management members select their function staff; function staff members select patrol staff. “Form” means appoint an accountable lead, agree a charter and interfaces, and establish an initial capable team; scale patrol staffing as demand becomes known. Existing tools can support early work while the planned systems are built or configured.

Tenant creation and first-admin assignment precede occasion creation; tenant admins create the occasion and assign occasion admins; recruitment opens only after the required intake, safeguards, notices and retention controls are accepted. These technical authorities remain distinct from the Board/chief appointment chain.

## System build priorities

System IDs retain their source numbering; order is the recommended **first useful delivery**, not a mandate to finish each entire product before starting the next. P0 includes reusable platform capability and planning slices; P1 adds intake/planning services; P2 accepts operational integrations; P3 completes rehearsals and coverage across all systems. The existing core datastore is assumed in place: system 21 work verifies and extends its contracts rather than rebuilding persistence.

Every application inherits tenant > occasion scope, canonical identities, current authorization, accepted-event provenance, rights/expiry interfaces and scoped background MVs. Integration acceptance applies equally to externally built products. Procurement/configuration/adapter work counts as delivery; bespoke implementation is not mandatory. Dependencies below concern the required slice, not every feature of the referenced system.

Dates, staffing levels, and build scope should be fixed once site commitments, registration milestones, procurement lead times, and delivery capacity are known.


## Revised release gates

**Foundation acceptance:** With the datastore already available, accept tenant/occasion separation, self-service first-admin creation, organizational operator attribution, current authority, scoped publication, incremental MV recovery, identity/content erasure, and replay/restore suppression before onboarding personal-data consumers. Basic planning and notification slices can use approved existing tools.

**Recruitment opening:** This is a gated occasion transition, not automatic success after creating an occasion. System 3 intake, required system 2 safeguards, notices, retention/expiry, restricted rights handling and reliable notifications must be ready. Participant registration has its own later acceptance gate.

**Application admission:** Each of 25+ integrations must demonstrate scope isolation, permitted identity mappings, field/purpose controls, provisioning/revocation and deletion/restriction outcomes, transfer/processor review and operational ownership. More application entries do not automatically require more bespoke systems.

**Operational readiness:** Complete emergency communication, site protection, monitoring and incident response before their actual build risks arise. P3 is a cross-system acceptance/rehearsal phase rather than a delayed start for reporting. Accept full trading, meal, movement and participant-support workflows before public opening, with safe behavior when identity/content references have been cleared.

Order changes principally bring the WorkItem spine, MV/reporting foundation and basic communications into P0, put the shared safeguards slice ahead of recruitment, and make privacy/application admission first-class gates. Operational systems retain demand-driven deadlines; early hardware and vendor feasibility work can proceed alongside foundations without premature personal-data activation.
