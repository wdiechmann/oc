# Local monitoring rehearsal — 26 October 2026

Local workstation, PostgreSQL 14.21, Elixir 1.20.3/OTP 29, Ruby 3.4.4. A separately named synthetic EP database and temporary EP listener on port 4181 were used. Fake `.example.test` identities and the private development notification sink were used; no external email or production backup was accessed. Temporary databases/artifacts were removed after verification.

| Check | Observed result |
|---|---|
| EP contract/security/privacy tests | `mix precommit`: 92 tests pass, including source revocation, scoped assignment, alert window/cooldown/suppression, idempotent claims/outcomes, ambiguous delivery, diagnostic access/expiry, erasure, late buffered records and retention checkpoint continuity. |
| TOM | 51 tests / 409 assertions pass; six JavaScript operation/reconciliation tests pass; RuboCop and Zeitwerk checks pass; Brakeman reports zero security warnings/errors. |
| Collector | Eight tests / 43 assertions pass: quota/expiry/encryption/lease/retry/quarantine, independent outage/recovery, actual TCP liveness/readiness/metrics and authenticated backup-vault tamper rejection. |
| Real TOM → EP integration | Rack integration against the real temporary EP HTTP API verifies operator sign-in, source/rule settings, named assignment, restricted diagnostic read, explicit global view, development-sink acceptance and no resend of terminal attempts. This is not a browser test. |
| Independent outage | Stopped only the temporary EP process; after three probe failures the independent collector wrote a private notice, retained one encrypted pending observation and returned HTTP readiness 503. Restarted EP; collector recovered after three successful probes, drained its queue and returned readiness 200. No lost/rejected records in that rehearsal. |
| Cross-language buffer | EP wrote an AES-GCM spool record; the Ruby collector authenticated/decrypted/claimed/acknowledged it successfully. |
| Bounded local workload | 200 new observations, 10 concurrent producers, 10 sources; all returned 201. Elapsed 0.506 seconds, 394.9 requests/s, p50 21.9 ms, p95 46.3 ms, maximum 50.4 ms. Monitoring pending publication count subsequently reached zero. |
| Backup/restore | Captured a snapshot-consistent encrypted PostgreSQL dump and signed identity-hash manifest; generated a newer signed two-subject erasure ledger and affected-copy worklist. Restored to a new loopback sandbox with matching PostgreSQL 14 clients, applied the ledger, verified zero pending monitoring erasures and removal of the planted `RestorePrivacyMarker` diagnostic. Original copies were preserved throughout verification; no automatic original retirement or publication occurred. |
| Crash recovery | A fixture process exit exposed orphaned executing publication jobs. Added startup/periodic pending recovery and Oban lifeline rescue, retaining idempotent consumers and no replayed notification side effects. |

The first backup attempt used PostgreSQL 17 client tools against server 14; its restore was incompatible. Capture now rejects client/server major mismatches and supports `EP_MONITOR_PG_BIN`; the successful rehearsal used matching version 14 tools. The live HTTP health test also exposed a Ruby rescue-expression branch that always returned unavailable; it was corrected and is covered by a real-socket regression test.

This workload is a short development-mode smoke measurement, **not** a sustained capacity test, database failure storm, high-availability rehearsal or evidence of support for 40–80,000 concurrent users. The shared machine is not an independent host failure domain. Playwright MCP was unavailable, so desktop/mobile rendering, focus/accessibility and real-browser reconnection checks remain pending. Monitoring-only restore cleanup does not erase core identities, other business domains, ordinary logs, attachments or vendor copies; the restored database stayed unpublished.
