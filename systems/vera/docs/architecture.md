# Architecture

VERA owns its web presentation and client session; EP owns canonical identity, authorization, accepted facts, transactional finance guards and query projections. The app intentionally excludes Active Record/Active Job/Action Cable and has no database configuration. No runtime dependency on TOM is introduced.

`HomeController → Views::Home::Index → Components::Layout` renders the static shell without calling EP. `EpHealthController → Ep::Client → EP /health/ready` provides dependency readiness using a fixed configured HTTPS origin or loopback HTTP origin, short timeouts, no redirect following and no automatic retries. A response must be 200 JSON with status ready. No browser credentials are forwarded. Authentication is implemented as described below; financial commands and monitoring-source registration remain next work.

Phlex uses explicit Views and Components autoload namespaces; Turbo and Tailwind assets are served locally. A content-security policy permits same-origin scripts/styles with a style nonce for Turbo, and arbitrary request parameters are filtered from logs. VERA uses its own Rails secrets and future backend credential; there is no shared TOM cookie/secret store. Production requires its own deployment secrets and HTTPS configuration.

## Thin sign-in

VERA POSTs /api/v1/auth/sign-in-links with its own backend credential. EP issues only for an active verified existing identity and binds the challenge to that identity and requesting backend. GET /session/verify stores the short-lived pending value in VERA's encrypted HttpOnly cookie; POST /session confirms through EP's existing verification API. Session rotation drops pre-login state; only the opaque EP session and expiry are retained. EP checks identity/session and current grants on protected calls. GET /me/workspaces provides current navigation, not a financial permission grant.

DELETE /api/v1/auth/session revokes only the presented session. VERA clears its cookie even if EP is unreachable, with an uncertainty notice. TOM's independent session remains valid. No SSO redirect protocol, shared cookie or duplicate invitation/recovery workflow is added. VERA delivers its own ephemeral sign-in message as the calling backend under the existing EP API handoff contract.

Local operator setup creates matching private configuration copies for EP's `vera` registration and VERA's own credential. Production uses deployment secrets and HTTPS application origins. Exceptions/parameters are sanitized and known form errors stream into vera-feedback. Full operational monitoring ingestion remains pending.

## Book context implementation

BooksController uses Ep::Client book API methods; Phlex book views/components hold only display data and unsaved form state. EP persists canonical setup events, protected book state and an outbox in one transaction. One tenant-local finance_books metadata stream orders hierarchy changes; future journals/payments are not serialized on that stream. Oban builds the incremental book MV. VERA's normal reads use that API projection and compare accepted/source revisions; no local database is introduced.

Forms carry a scoped per-session idempotency key and expected projected book version. EP revalidates current access and hierarchy under tenant-local locks. A cycle/stale edit stays inline with the draft preserved. Unknown transport outcomes retain the original command type/key for a user-initiated GET-only completion check; the check never repeats the mutation. Forbidden/stopped views do not masquerade as current data. This initial metadata slice provides explicit refresh, not cross-user push subscriptions.

Current tenant admins provision book context metadata; neither tenant/occasion nor platform monitoring roles are interpreted as finance posting/payment grants. Occasion-only admins have no tenant-book setup surface. Book-scoped stewards and occasion bindings are implemented below; broader finance grants and activation remain later work.

## Finance setup implementation

FinanceSetupController and Phlex components use the versioned EP setup API, documented in [the finance setup contract](../../ep/docs/finance-setup-api.md). Protected SetupState, Steward, Binding and Account rows enforce acceptance; a book-local lock serializes role changes and setup commands, while a tenant/occasion lock protects competing bindings. The initial AccountCreated event ID is the stable account ID. Account snapshots carry authenticated operator and backend application attribution. Tenant administration may assign/revoke roles, but configuration mutations require an explicit active book grant.

A separate finance_setup stream per book publishes accepted setup snapshots through outbox/inbox and SetupWorker to SetupView. The tenant's finance_setup MV control gates reads and delivery. SetupProjector supports safe rebuild, and pending-outbox recovery schedules setup workers. Routine account/binding display uses this MV; current grant/candidate checks are restricted control data. Workspace navigation includes only currently granted book links with running query controls.

Signed, expiring form tokens bind tenant/book/action/account and a random command key to the current VERA session. Accepted/source revisions distinguish pending projection. On a known conflict VERA re-renders the submitted draft above the latest projected accepted row; reapply uses current versions and a fresh key. On unknown outcome the encrypted session retains the original command/key/body and disables new saves until reconciliation. GET completion only reads the private receipt. After an unknown receipt, a separate CSRF-protected explicit retry submits the original stored body/key, never edited replacement fields. No local financial database or automatic transport retry is introduced.

## Chart pages and browser editor

ChartAccountsController reuses the existing signed command tokens, EP mutation/receipt handling and exact-original retry workflow, but renders a separate chart view. EP's GET setup/accounts endpoint filters/sorts the setup MV in canonical position order and returns at most 100 rows (50 by default), pagination totals and book-local VAT/category entry options. will_paginate wraps the remote page as a Collection without an Active Record dependency. Stable source revisions fence infinite-scroll requests, avoiding mixed-generation pages when rows move or change.

The locally served chart_editor module defines a native coa-editor custom element. It delegates line-edit/type-toggle and keyboard events, pauses infinite loading while a line is open, and uses IntersectionObserver plus same-origin GET Turbo streams to append pages and replace pagination controls. Normal will_paginate links remain available. Home/End and page keys can navigate to unloaded first/last/adjacent pages; inputs retain native editing keys. A changed revision stops appending while keeping the editor; stopped/revoked access clears the protected surface. Server-rendered conflicts preserve the draft above the newer accepted line. Acceptance can trigger read-only refreshes until projection catches up; mutations are never automatically retried.

EP stores stable VAT/category references with acceptance-time codes/versions, canonical integer position, formula text and stable formula_refs. Its restricted arithmetic parser validates syntax/references and detects cycles without executing text. Number references bind to initial account event IDs; unchanged expressions remain pinned across renumbering. Stable UUID references support unnumbered calculations. Legacy event snapshots normalize heading/total row types and gap-spaced positions during replay; the schema migration preserves former number reservations and supplies no fictional calculated values.

## Accounting period control

PeriodsController reuses signed per-session form keys and the financial operation receipt/retry mechanism through command_type/execute_command hooks; period requests use FinancePeriod:<action>, independently from FinanceSetup receipts. Separate Phlex period views show inclusive dates/status/history, draft correction forms and state-dependent actions. Known conflicts preserve submitted date/reason drafts, including readonly recovery when another operator has opened/reopened the period. Unknown outcomes retain the original body/key; completion is GET-only and explicit retry sends that unchanged command. If access is revoked during a retry or subsequent view, protected content is cleared but the original private receipt remains available for reconciliation. Role assignment uses a separate reopening_authority setup command; no grant is created by migration.

EP's Periods module uses protected PeriodState/Period rows and a book-local finance_periods stream. The shared setup-authority lock orders role revocation with period commands; the registry lock and expected registry/period revisions protect overlap/status changes. Reopen checks can_reopen_periods on current active stewardship. Period transitions/draft corrections take FOR UPDATE; the internal lock_open! date guard takes FOR SHARE and must remain in a future authorized posting transaction through ledger/event commit. This slice provides no journal/posting endpoint or book activation.

Outbox/PeriodWorker/PeriodProjector maintain the independent finance_periods MV and complete period transition history. Serving/delivery refuses stopped controls; pending-outbox recovery queues the period worker. Operator-only projector rebuild validates ordered scope/status/immutable-date history and creates no accepted facts/jobs. For protected-state verification, use an isolated replay of finance_periods events: fold each period's latest accepted snapshot and stream checkpoint, then compare its ID/book/tenant/name/dates/status/version/actor/application/reason and the registry version with the protected tables. Never repair live protected period state through manual SQL; reconcile/rebuild under an operator-controlled write pause before admitting journal handlers.

## Catalogue references and adoption

Catalogue entries use protected finance_catalogue_entry rows, stable UUIDs, kind, mutable code/name, reserved former codes, active status and accepted setup version/actor/application. They share finance_setup commands, receipts, lock, revision, outbox and serving controls with chart configuration. Current-protected entry checks guard assignments; projected labels/options never authorize writes. The setup projection derives catalogue history from entry revisions, carrying history unchanged through unrelated account/role events. Replay only rebuilds query data.

A steward explicitly invokes catalogue_initialize once per book. One accepted batch creates the former three VAT/five category labels, binds current legacy account selections to their UUIDs, bumps affected account revisions and marks the setup initialized. It preserves account identities, selection meaning and old event payloads. No initialization occurs in migrations or reads. New catalogue creates use their initial event ID; batch-adopted entries have separate stable UUIDs within the batch event. The schema migration only adds tables/nullable reference columns/initialization state.

The chart endpoint joins current projected entry labels and supplies structured entry options with id/code/name/kind/active/history. New VERA dropdowns submit UUIDs and expose active entries plus the row's own retained inactive choice. Before adoption the new chart is readonly; compatibility API clients may keep former validated string selections until initialization. After initialization compatibility strings resolve current codes, or retired aliases only for the account's own existing association. Each new account revision captures selected IDs/versions and the current code strings; catalogue edits alone never rewrite accounts. CataloguesController reuses the signed setup command and private receipt/retry lifecycle with catalogue-specific routes and preserved conflict forms. Tax rates/rules and reporting mappings remain separate future contracts.

## Reviewed chart transfer

`ChartCsv` parses bounded UTF-8 CSV into string arrays and safely encodes exports; it never evaluates formulas or coerces account numbers. VERA holds no local business records. EP stores expiring identity/backend-private uploads, validates mappings and builds a non-writing final-state plan with the shared `AccountRules`/catalogue/formula validators. The review digest binds the source, mapping, owner/backend, revision and assigned event/account identities. Acceptance reauthorizes current stewardship before receipt replay, rebuilds the plan under the setup lock, then commits all changed account rows, individual events, outbox entries and one receipt atomically. Position uniqueness is deferred only inside import acceptance, allowing final-state swaps. Missing rows are retained. Unchanged rows emit no events.

Import account events contain per-account patches; existing single-line setup snapshots remain replay-compatible. The setup worker finishes the final command group beyond its page limit in one transaction, preventing partial import publication. A scheduled cleanup worker removes one-hour drafts; original command receipts survive cleanup. Read exports use one ready projected snapshot rather than accumulating pages. VERA signs import ID/digest/revision and stores only that small acceptance pointer/key in its existing unknown-outcome session recovery. Template/export endpoints require current EP access and use no-store responses. See `systems/ep/docs/chart-csv-api.md` and `chart-csv-openapi.json` for the contract.

Import code creation uses non-writing provisional catalogue entries with pinned IDs/versions, passed through the same reference validators as accepted entries. Re-preview binds the explicit create_codes flag and catalogue proposals into the digest; acceptance reconstructs them against current protected state, then emits catalogue patches before account patches in the shared setup stream. Catalogue history and atomic whole-command publication survive replay.

Regional CSV upload: separator detection and empty-row skipping happen in VERA’s bounded string parser; EP’s review and financial validation remain authoritative.

The shared catalogue code validator accepts bounded descriptive Unicode text for manual setup and CSV proposals. VAT/category lookup, uniqueness, reservations and accepted account associations remain scoped by book/kind. Identical text in different kinds yields independent UUIDs; descriptive values round-trip unchanged.

Replacement imports add explicit retirement to protected accounts. A generated UUID position scope assigns all current accounts the same scope and each retired account its own historical scope, preserving positions under the existing deferred unique constraint. Book/account-number uniqueness and reserved-number guards remain unchanged. Import plans validate only successor rows in replace mode, all current rows in merge mode, and append complete before/after retirement patches after account changes. Matching retired identities can emit AccountRestored; AccountRetired marks inactive history without deleting rows or prior facts. Setup MVs retain both populations; serving current/export filters retired rows, while retired=1 provides bounded read-only history. Line commands reject retired IDs. Digest/mode/version/authority and atomic projection-group guards remain shared.

## Position-only order reviews

`ChartOrder` uses the existing expiring private review storage with purpose `chart_order`, separate native endpoints and `FinanceChartOrder:accept` receipts. Explicit purpose guards prevent cross-use with CSV reviews. GET uses one ready setup MV snapshot; preview/accept validate the complete protected current account set under the setup lock. Deterministic 100-step positions and pinned per-row event IDs are reviewed against the setup version. Acceptance rebuilds the plan and updates only positions/revisions/attribution; catalogue snapshots, formula text/references and all identity/lifecycle fields are preserved. The existing deferred position constraint and atomic command-group projection/rebuild support swaps without partial visibility. VERA submits only UUID order/revision for preview and a signed small review pointer for acceptance, storing no local business database. Existing cleanup purges drafts while receipts remain replayable.

## Effective VAT configuration

Protected VatRule rows bind to book-local VAT UUIDs and are governed by the existing setup lock/stream/receipt flow. Setup snapshots include rule configuration; the shared projector builds immutable rule histories and retains them through CSV/native-order account patches. Active inclusive ranges are checked under the shared book lock. Integers represent hundredths of a percent; protected quotes use exact signed integer arithmetic and configured reporting sums. lock_rule! canonicalizes scope and keeps the book advisory/selected-row share locks inside a caller-owned acceptance transaction. No financial execution is activated. VERA transports percentages exactly as integer basis points, renders projected histories, preserves drafts, and reconciles unknown outcomes with the original command. Preset drafts are supplied by EP; no rules are automatically seeded.

## Danish VAT preset drafts

Effective VAT rules offer 16 versioned Danish templates, including domestic VAT, qualifying restaurant/hotel deductions, EU/non-EU trade and domestic reverse charge. Selection fills an editable draft with source links and usage conditions; effective dates remain blank. Only a unique active alias match suggests a VAT entry, with UEUV distinct from UEUV2. Importing labels never accepts tax rules. Accepted rules and histories pin the source version and track customized values. Imported-goods assessment requires an explicit customs-statement VAT amount rather than calculating from supplier net. EP owns validation, calculation and provenance; VERA has no local policy database. See ../../ep/docs/danish-vat-presets.md.

## Chart formula preview

FormulaPreview reads a bounded complete ready Setup snapshot under existing current read authorization. Formula validation and preview share a data-only AST parser. The evaluator resolves accepted formula_refs without rebinding numbers, caches exact reduced integer fractions, traces direct dependencies and deduplicated posting inputs, and bounds dependency depth, evaluation steps, precision and amounts. Read-only POST calculations require a matching source revision and current book-local posting UUIDs. VERA transports integers through Ep::Client and renders Phlex; no formula arithmetic or business database exists in VERA. Amounts remain request-local, outside session/URL/log payloads.
