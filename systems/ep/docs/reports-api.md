# Reviewed report definitions and test previews

All routes under `/api/v1/tenants/:tenant_id/finance/books/:book_id/reports` require a registered backend and current EP session. Tenant administrators and explicit book configuration stewards can inspect definitions/history and test balances; only current explicit stewards can prepare private reviews and accept changes. Book hierarchy grants no access. Rules remain EP-owned; VERA has no business database. This is local report configuration and test arithmetic, not ledger reporting, consolidation or posting.

- `GET /?report_id=uuid&version=integer`: index, freshness, current authority, current posting-account options and optionally a selected accepted report revision. Omit version for current. Index histories expose actor/application/acceptance time; selected definitions retain account labels/versions, chart source revision and stable line UUIDs. Invalid report/revision is 404. Inactive reports remain inspectable.
- `POST /reviews`: `{report_id: uuid|null, expected_report_version: integer|null, expected_version: integer, name: string, active: boolean, lines: [...]}`. Each line is exactly `{id: uuid|null, code, name, kind, position, account_ids: [uuid], sign: 1|-1, formula: text|null}`. Null IDs create stable identities; existing IDs retain identity. Name is trimmed Unicode 1–120 characters without control/format characters. Codes are case-sensitive, start with an ASCII letter, and contain up to 40 letters/digits/periods/underscores/hyphens. Positions are unique positive integers. Types: header (no accounts/formula), mapping (current book-local posting IDs, uniform signed sum), total (report-line arithmetic, no account selections). Mapping inputs may include inactive current posting accounts, explicitly marked; retired/cross-book/header/calculation chart IDs are rejected. Empty mapping rows evaluate to zero and are flagged.
- `GET /reviews/:review_id`: private identity/backend/book-scoped review; no definition has been accepted. Shows before/after, coverage, bound digest, expected setup revision and one-hour expiry. Existing cleanup workers remove expired drafts.
- `POST /accept`: `{review_id, digest, expected_version}` plus Idempotency-Key. Current stewardship precedes replay. Same setup lock/stream/version as account configuration. Acceptance rechecks scope, review purpose/expiry, setup freshness/revision, digest and original report version, then atomically appends ReportDefinitionCreated/Revised, protected definition, setup snapshot, outbox and private FinanceSetup:report_save receipt. A different key cannot accept the same review again. The same original key/pointer resolves an accepted receipt even after review expiry. VERA saves only this small pointer in its bounded unknown-outcome session, never the definition or test balances.
- `POST /:report_id/preview`: exactly `{report_version: integer, balances: {posting_uuid: signed_integer_minor_units}}`. Reads the explicitly selected accepted revision, including older or inactive revisions, from a ready authorized view. Balance IDs belong to that revision's saved posting-account universe; amounts bounded to ±9,000,000,000,000. Blank/missing is unknown, not zero. No balance, fact, receipt or journal is persisted.

Totals use the shared safe chart-formula grammar: bracketed line codes/`[@line_uuid]`, exact decimal constants, unary signs, parentheses and normal +,-,*,/ precedence. Bind references to line UUIDs at acceptance; an unchanged formula retains its original bindings through line-code/name/position changes. Codes remain reserved to their original UUID even when a line is removed, preventing historical reinterpretation. New/changed formulas bind against the proposed complete definition; missing references, headers and cycles are rejected. Display order never determines membership.

Report revisions snapshot the posting-account universe and mapped account labels/versions at review. Later catalogue/account edits or whole-chart replacement do not rewrite accepted definitions/history. Historic previews use those saved identities and supplied test balances, even if accounts were subsequently retired. A new report revision requires current posting references, so retired mappings must be explicitly removed/remapped. The UI distinguishes saved coverage from current-chart coverage: unmapped posting accounts, accounts assigned to multiple mapping lines, empty mapping lines and unavailable mapped accounts. Multiple assignments are warnings rather than automatic exclusions; user-defined totals can intentionally count an account more than once.

Mapping lines sum their explicit account balances and apply the selected sign. Totals retain reduced exact fractions through nested lines; only displayed amounts round to nearest minor unit, half ties away from zero. Results include signed amount, exact numerator/denominator strings, direct line bindings and deduplicated underlying posting inputs. Dependency lists do not attribute nonlinear contributions. Per-line errors identify missing balances, invalid references, division by zero, complexity or amount limits and propagate to dependent totals without invented zeroes. The report version and chart cutoff remain explicit. No currency conversion or period/book consolidation is inferred.

Limits: 20 definitions per book, 50 lines per definition, 2,000 current posting accounts, 4,000 account assignments; formulas ≤2,000 bytes. Preview inherits bounded exact arithmetic and operation/dependency tracing from FormulaPreview. Responses are no-store. Request payloads are filtered from VERA logs; test balances stay outside URLs/sessions/storage. Shared setup projector/rebuild retains immutable report revision history through ordinary setup and account-patch events.

Errors: 401 authentication, 404 scope/report/review authority, 409 stale/pending setup, digest/idempotency/already-accepted conflicts, 410 expired review, 422 invalid report/line/reference/balances or reserved code/limits, 503 stopped/unavailable view. Unknown acceptance requires receipt check before explicit unchanged retry; read-only preview can safely be repeated. Storage migration seeds no definitions or financial data.
