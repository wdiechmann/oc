# Chart formula preview

Registered backend and current session required. Tenant administrators and explicit book stewards can inspect the current book's accepted chart and perform read-only test calculations. Hierarchy confers no access. `Setup.get` holds the current authorization/setup guard while capturing one projected revision; stopped views fail and pending views cannot preview. Current rows include inactive accounts but exclude retired history. The limit is 2,000 rows, independent of chart pagination/search. Preview accepts no formula text or configuration changes and creates no event, receipt, review, balance or journal.

Routes under `/api/v1/tenants/:tenant_id/finance/books/:book_id/formula-preview`:

- `GET`: returns tenant/book/name, source_version, current rows (stable IDs, numbers, names, row type, active state, formula text, pinned formula_refs, position/version), empty balances and null results.
- `POST`: exactly `{expected_version: integer, balances: {posting_account_uuid: signed_integer_minor_units}}`. Version must match the ready chart snapshot. Supplied balances must belong to current posting rows in this book, each bounded to ±9,000,000,000,000. Missing is unknown, not zero; explicitly supply zero when known. No idempotency key is needed: repeat calculation is read-only. Response includes submitted balances and per-calculation results in chart order.

Formula validation and evaluation share a parser for bracket references, decimal constants, unary signs, parentheses and left-associative +, -, *, /. Multiplication/division have normal precedence. No runtime code evaluation, range expansion or position-based membership. Resolve references only through the accepted `formula_refs` map; never silently bind an old label to a new account with that number. Nested calculations can be referenced as `[@account_uuid]`; bare numbers inside brackets identify the saved binding. Headers or missing/retired identities are invalid. Inactive current identities remain visible and explicitly marked.

All balances and literal constants use minor-unit quantities. Decimal constants can express fractions/scaling; the formula language does not infer money dimensions. Calculations use reduced exact integer fractions through nested references, not rounded child displays or floating-point arithmetic. Each displayed amount rounds to the nearest minor unit with half ties away from zero. Successful results include account_id, status=ok, amount_minor, exact `{numerator, denominator}` as decimal strings, direct reference bindings/values, and deduplicated underlying posting IDs/names/balances. Inputs are dependencies, not an additive contribution attribution for nonlinear formulas. Each completed calculation must remain within the amount bound; exact fractions are limited to 60-digit numerator/denominator, recursive dependency evaluation to 64 frames, and the full preview to 100,000 evaluation steps (including dependency-set and breakdown work).

Per-row errors: missing_balance (with related posting ID), invalid_reference, formula_cycle, invalid_formula, division_by_zero, complexity_limit, amount_out_of_range. Unrelated valid rows can still calculate until the global complexity budget is exhausted. Errors produce no misleading zero/result. Top-level errors: 401 authentication, 404 current scope/authority, 409 view_pending/version_conflict, 422 invalid_preview/invalid_balances/chart_too_large, 503 stopped view. Responses are no-store. Test balances are request-local, absent from query URLs and not persisted. VERA filters financial request fields from logs.
