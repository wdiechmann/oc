# Work-in-progress journal rows

The current journal UI creates a journal from name, date and reference, then opens its line editor immediately. All work remains unposted. Authorization, verification, balancing for final acceptance, VAT ledger splitting and posting are later workflow stages. Current book stewards may edit drafts; administrators inspect. Existing explicit-review journal APIs and historical snapshots remain readable for compatibility.

The row editor shows immutable human ID, line reference, enclosure icon/count, debit posting-account lookup, decimal amount, credit posting-account lookup and account-driven VAT results. A row can have both accounts (paired debit/credit with one amount), one account (unfinished/compound work), or remain incomplete. Save preserves issues rather than claiming authorization. Each successful edit appends a journal-draft revision; Enter saves and Escape cancels local edits. Only one row may be dirty at a time. Header edits revalidate the journal date/context without renumbering rows.

## Human posting IDs

One counter spans every journal in each book; it never resets at a journal or period boundary. IDs are allocated only when a work row is committed, in the same PostgreSQL transaction as its protected row, journal fact and receipt. The counter is transactional state, not a PostgreSQL sequence: rejected saves, rolled-back transactions, previews and retries consume no numbers. IDs are unique on (book_id, posting_id), returned with successful row saves and suitable for handwriting on physical enclosures. Replaying the original command returns the same row/number.

Numbered rows cannot disappear or move to another book/journal. Void retains the row, number, enclosures and history; restore reuses the original number. The gap-free audit register therefore includes voided work. Future financial posting must retain the work row's ID for its resulting transaction group (including generated VAT legs) and use this same book allocation policy for other transaction origins. This slice creates no posted financial transaction.

## Amounts and VAT

Books currently support DKK, EUR, SEK, NOK, GBP and USD, all represented with two decimal places in this editor. VERA accepts comma decimals outside English/US locales and dot decimals in English/US locales. No grouping separators, float parsing or guessed punctuation: `125,50` in Danish and `125.50` in English both transport 12550 integer minor units. Too many decimals and mixed punctuation fail visibly. Work-row amounts may be signed; negative values reverse the draft debit/credit side while retaining nonnegative leg amounts. The form's signed locale survives receipt recovery; retry transports the original parsed integers.

VAT inclusion defaults to the selected account’s nullable vat_basis (gross or net). A posting checkbox overrides it for that row; Use account default clears the override. Existing unspecified defaults and conflicting taxable-account defaults require an explicit posting choice before a VAT quote is available. VAT entries come from selected accounts, never imported account names or guessed rates. Ordinary input/output gross VAT is rounded directly as gross × rate / (10000 + rate), with net the exact remainder, preserving small-amount rounding. Net entry uses the existing exact rule calculator. Output VAT follows the credit-positive/debit-negative convention; input/reverse charge follows debit-positive/credit-negative. VAT amounts are summed in the compact cell; hover text retains the individual quotes. Reverse charge uses the invoice base; import statements still require externally assessed VAT and remain a visible draft issue when it cannot be derived from amount alone.

VAT previews use the protected current date/rules, require the displayed draft/context cutoffs, and write no review, row or number. Save independently revalidates. Entered debit/credit work values and VAT evidence are retained; actual net/tax posting legs require the later authorized/verified posting workflow. Historical snapshots retain earlier amounts, rules and interpretations.

## APIs

All routes under `/api/v1/tenants/:tenant_id/finance/books/:book_id/journals` require backend/session authentication and current book authority.

- `POST /work/create`: `{contexts, expected_version, initial_row?:boolean, data:{name,posting_date,reference}}`. With initial_row=true, atomically creates the journal and its first empty numbered line and returns row_id/posting_id; attachments work immediately. Omitted/false preserves the legacy header-only behavior.
- `POST /work/details`: `{contexts,expected_version,draft_id,expected_draft_version,data:{name,posting_date,reference}}`. Preserves rows/IDs and revalidates under the changed header.
- `POST /work/row`: `{contexts,expected_version,draft_id,expected_draft_version,row}`. Row is exactly `{id:null|uuid,reference,debit_account_id:null|uuid,credit_account_id:null|uuid,amount_minor:integer,amount_basis:null|gross|net,basis_override:boolean,void:boolean}`. Saved data includes server-owned posting_id, stable leg IDs and enclosure metadata. Submitted posting IDs are not accepted. Work mutations use Idempotency-Key and private `FinanceJournalWork:create|details|row|attachment` receipts. Recovery stores only the bounded original command/pointer, never file bytes. Current authority precedes replay; source/draft changes require explicit resubmission of the preserved row with fresh fences.
- `GET /accounts?q=...`: bounded current active posting-account matches (number/name), max 20, with setup source_version. The Carla-style client requires `/`, debounces, aborts stale lookups, supports arrows/Enter/Escape, and persists the selected stable UUID rather than free text. Inactive/retired selections remain visible for correction; header/calculation rows never appear in results. Source changes fail closed.
- `POST /row-preview`: `{draft_id,expected_draft_version,contexts,row}`. Read-only account-driven VAT/validation evidence. No numbering or persistence.
- `GET /rows/:row_id/attachments`: authorized current row number and accepted enclosure metadata.
- `POST /rows/:row_id/attachments/stage`: `{filename,content_type,content:base64}`. Identity/backend/book-private one-hour upload staging, using existing cleanup infrastructure. PDF/PNG/JPEG only, checked signatures, max 5 MiB, simple filenames ≤180 characters. Staging allocates no number or accepted enclosure.
- `POST /work/attachment`: `{contexts,expected_version,draft_id,expected_draft_version,upload_id}`. Atomically binds staged bytes to their original row and saves a draft revision, preserving its number. Max 20 enclosures per row. File metadata includes SHA-256, MIME/size; events/sessions contain metadata/pointers only, not file contents. File-bearing SQL writes suppress parameter logging and HTTP financial fields are filtered.
- `GET /attachments/:attachment_id`: current authorized download metadata/base64. VERA relays as a no-store attachment with nosniff. Bytes are stored privately in EP, not a VERA business database or public asset URL. Voiding a row retains its enclosures.

Legacy draft lines enter the new editor as one-sided work rows. Their original snapshots remain in History; the next explicit save adopts the new account-driven interpretation and numbered row registry. A book's protected journal/counter guards serialize writers; number uniqueness and row/draft scope constraints reinforce acceptance. Query rebuild replays accepted snapshots without allocating numbers or uploading files. No final posting authority is granted by these endpoints.

New saved rows prepend the journal list; existing row edits retain their position and posting number. The optional nullable `credit_amount_minor` is a user override (integer −9,000,000,000,000–9,000,000,000,000); null requests calculation. Returned rows include `suggested_credit_minor` and effective `credit_total_minor`. EP derives the invoice total from the first VAT-configured selected account (debit before credit), using the row gross/net choice and effective rule; no VAT configuration uses the debit amount. Missing basis/rules/assessment leave the calculated amount null. Gross ordinary VAT preserves the entered total; net adds VAT; reverse charge/no-VAT retains the invoice base. Credit leg draft values use the effective credit total; final tax ledger legs and balancing remain later work. Saved older rows retain their original equal credit when edited unless explicitly reset to calculation. Previews return these fields without allocating a posting ID.

VERA creates journals with `initial_row: true`. New line explicitly commits an empty row through `/work/row` before opening its editor; no mutation occurs on GET. Empty and voided lines remain in the gap-free audit register. A row’s first account/amount edit and its attachments keep the allocated ID.

`POST /work/row` optionally accepts `append_row:true`. EP updates the selected row and prepends a new empty numbered row in the same acceptance transaction, returning `next_row_id`/`next_posting_id` alongside the edited row’s IDs. Rollback and original-key replay cover both changes. The 100-row bound remains; VERA Enter requests append only while there is room. Menu Save keeps its existing save-only behavior.

Account lookup uses case-insensitive literal substring matching from two trimmed characters, across posting account number/name, VAT code/name and category code/name. Exact account numbers sort first; at most 20 active, non-retired book-local posting accounts are returned. A one-character query returns no results; no slash prefix or regular expression syntax is required. Lookup stays read-only and authority/version scoped.

Credit suggestions now use the net component, excluding ordinary VAT, rather than the invoice total. With a configured 25% rule, gross 112500 minor units yields credit 90000 and VAT 22500; gross −112500 yields −90000 and VAT −22500. Net entry keeps the entered net amount as the credit suggestion. Both sides retain exact integer rounding; manual credit overrides remain explicit. Normal VAT work-row quotes carry posting_direction=input for positive debit and output for negative debit. This is the intended VAT counter-leg direction; configured rule provenance/reporting evidence stays intact, and final tax-account posting remains a later workflow.

Lookup also returns a uniquely matching short account number for exact resolution when leaving an input; broad partial matching still requires two characters. VERA only auto-selects a unique, literal exact account-number match and rechecks the source cutoff. Prefix/name matches still require an explicit selection.

## Complete saved posting preview

Validation now includes `posting_preview` with status (`complete`/`needs_attention`), `unposted:true`, debit/credit totals, difference, balance, error codes and per-row legs. Each row retains its posting ID, selected VAT rule/version/date and account UUID/number/name/version on every leg. These are immutable accepted draft evidence; no ledger entry or number is allocated by a read-only preview. Old histories without this field remain readable.

Ordinary gross 112500 with a configured 25% rule previews debit 112500, net credit 90000 and mapped VAT credit 22500. Net input 90000 uses gross debit 112500 in the complete preview, preserving the entered net work value. Signed negatives reverse the preview sides and select the outgoing role according to the journal’s configured sign convention. Incoming VAT is split into deductible input VAT and non-deductible VAT using the rule share; outgoing VAT uses the full amount. Reverse charge adds output VAT and balancing input/non-deductible components without changing the invoice base. No-VAT rows need no generated tax leg. Exact integer rule rounding is reused.

Missing mappings, inactive/retired accounts, missing assessment/rules, both selected accounts carrying VAT, incomplete lines, a non-open period or a manual credit that leaves a difference prevent a complete preview. Pristine empty entry rows and voided rows are excluded; enclosures or entered values make an unfinished row visible as an issue. Saved history keeps prior accounts/rules/amounts; current edits revalidate and produce new evidence. Completion/balance here does not authorize posting: financial authorization, verification, period locking at final acceptance and actual ledger execution remain later work.

Non-deductible VAT now follows the business account by default. The ordinary incoming-VAT credit suggestion includes the non-deductible share when no separate-account override is configured; the full preview folds that share into the same cost leg exactly once and records `non_deductible_vat_minor` for explanation. Thus gross 112500 with 50% deduction suggests cost credit 101250 and deductible input VAT 11250. With zero deduction, all 112500 stays on the cost account. Reverse-charge non-deductible VAT folds into the debit/business leg; the invoice credit remains its net base. Explicit separate-account and manual credit overrides remain explicit and balance-checked. Ordinary VAT row quotes expose `posting_vat_minor` for the displayed deductible/input or full/output amount, retaining full VAT/deductible/non-deductible amounts in the quote. Saved histories are unchanged.
